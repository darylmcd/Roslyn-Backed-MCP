## Acceptance

- [x] Root cause determined FIRST — corrected after a spec-compliance review rejected the first pass. CONFIRMED cause: hypothesis (b), specific path — `WorkspaceExecutionGate`'s own per-request timeout (default 2 min, `ROSLYNMCP_REQUEST_TIMEOUT_SECONDS`) arms an internal `CancellationTokenSource` linked to, but distinct from, the caller's ambient token. When it fires first (routine for a large/unfiltered `dotnet test` run; `TestTimeout` defaults to 10 min and never gets a chance to fire), the resulting `OperationCanceledException` is deliberately rethrown unclassified by both `RunTestsOnceAsync` and `StructuredCallToolFilter` (on the assumption any OCE means client cancellation) — but the MCP SDK's own top-level catch-all (`ModelContextProtocol.Core` 1.4.1, `McpServerImpl.cs`) only recognizes cancellation tied to the AMBIENT per-request token, so it falls through to its own hardcoded `"An error occurred invoking '{tool}'."` fallback: zero category, zero schemaHint, zero `_meta` — matching every repro verbatim, including the 2026-08-05 retro's measured 120.37s runtime (a near-exact match for the gate's 120s default). Hypothesis (a) (payload overflow) was never measured against the real MCP output cap and was NOT the confirmed cause. The originally-suspected escaping-`KeyNotFoundException`/`WorkspaceEvictedException` paths are NOT the cause — both are caught and reformatted by `StructuredCallToolFilter`'s generic catch before they ever reach the SDK boundary (pinned by `WorkspaceEvictionAutoRetryTests`).
- [x] Fix shipped per the determined cause — `WorkspaceExecutionGate.RunPerWorkspaceAsync` and `RunLoadGateAsync` now reclassify a gate-internal-timeout `OperationCanceledException` into a `TimeoutException` (mirroring the existing `GatedCommandExecutor.ExecuteAsync`/`WorkspaceValidationService` pattern) before it can escape unclassified; `ToolErrorHandler.ClassifyAndFormat` already maps `TimeoutException` to `category="Timeout"`. Genuine caller-initiated cancellation is left unclassified so it still reaches the MCP protocol-level cancel path. **`RunPerWorkspaceAsync`'s `try` was widened to also wrap `ApplyStalenessPolicyAsync`** (the auto-reload leg) after a second review pass found a gate timeout firing during that leg's `ReloadAsync` call escaped the original, narrower `try` unclassified — the identical bug via a code path the first fix-cycle missed.
- [x] Payload-pagination/truncation hardening from the first pass — REVERTED from this row (see Anchors above) and re-homed to `test-run-failures-pagination-truncation`; it implemented an unconfirmed hypothesis and does not belong in a root-cause row for a different, now-confirmed cause.
- [x] Regression: `WorkspaceExecutionGateTests.RunReadAsync_RequestTimeoutFires_ThrowsTimeoutExceptionNotBareOperationCanceled` (+ `RunLoadGateAsync_...` sibling) proves the gate timeout now surfaces as `TimeoutException`, not a bare/unclassified `OperationCanceledException`; `RunReadAsync_CallerCancellation_PropagatesAsOperationCanceledNotTimeoutException` proves true caller cancellation is untouched.

## Context

A full-suite (no-filter) `test_run` returned a bare "An error occurred invoking test_run" at server v2.3.1 even though the timeout/file-lock/build-failure `FailureEnvelope` (shipped via #108) is in place and the tool catches all exceptions (`ValidationTools.cs:178` → `ToolErrorHandler.ClassifyAndFormat`); the filtered `test_run` and `validate_workspace(runTests=true)` both worked (50/50 green).

NB: #611's original timeout-envelope ask is SHIPPED (#108) and its issue is closed — this is the distinct residual. **Second repro:** a COMPOUND `|`-OR filter (4 `FullyQualifiedName~` clauses) hit the same bare error at v2.3.0 (session b70ec703, 2026-05-27), while splitting it into 4 single-clause `test_run` calls each returned cleanly — supports hypothesis (a) (combined TRX output exceeds the MCP cap) over (b), and shows the bug is NOT unique to the unfiltered call.

**Post-review correction (2026-08-11):** a spec-compliance review of the first pass's fix rejected its root-cause claim — the "catch(Exception) wraps every exception" premise was false, and the payload-overflow hypothesis was never measured. Re-investigation traced the literal bare string to the MCP SDK's own top-level `tools/call` catch-all (`ModelContextProtocol.Core` 1.4.1, `McpServerImpl.cs`), which falls back to `"An error occurred invoking '{tool}'."` for any exception that is neither an `McpException` nor an `OperationCanceledException` tied to the AMBIENT per-request cancellation token. `WorkspaceExecutionGate`'s own per-request timeout (default 2 min) fires on an internal, gate-owned token — not the ambient one — and its resulting `OperationCanceledException` was deliberately (but too broadly) rethrown unclassified by both `RunTestsOnceAsync` and `StructuredCallToolFilter`. A large/unfiltered `dotnet test` run routinely exceeds 2 minutes (well before the 10-minute `TestTimeout` would ever fire), which is why the symptom correlates with "large/unfiltered" and is essentially exclusive to `test_run` among this server's tools. This is now fixed at the gate (see Acceptance above); the compound-filter repro's "one slow call fails, four fast calls succeed" shape is explained by duration crossing the same 2-minute ceiling, not by TRX payload size (which the original repro notes never measured).

**Second post-review correction (2026-08-11, same day):** a follow-up spec-compliance review found the gate fix itself incomplete — `RunPerWorkspaceAsync`'s original `try` block started AFTER `ApplyStalenessPolicyAsync` (the auto-reload leg), so a gate timeout firing during that leg's `_workspaceManager.ReloadAsync` call (which the method's own pre-existing comment already documents can consume "some, possibly all" of the request-timeout budget) threw the identical unclassified `OperationCanceledException`, via a code path the first fix-cycle missed. The `try` now wraps the staleness-policy/reload leg too. The same review also found the first-pass payload-pagination hardening (kept as "defense-in-depth" per the first correction above) was still out of scope for this row and reverted it, filing `test-run-failures-pagination-truncation` (Medium/M) to re-implement it as its own reviewed unit with an actual output-cap measurement; and filed `gate-timeout-exception-drops-inner-oce` (Low/S) for a smaller, separate finding — the new `TimeoutException` throws (here and the pre-existing one in `GatedCommandExecutor.cs:95`) construct message-only, dropping the caught `OperationCanceledException`'s provenance.
