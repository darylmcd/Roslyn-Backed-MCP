- **Fixed:** `test_run` can now execute TUnit test projects. TUnit is entirely built on Microsoft.Testing.Platform (MTP) and never registers with the classic VSTest adapter, so `--logger trx`/`--filter` were silently ignored for it. `test_run` now detects an MTP-only project and invokes it with the MTP-native argument shape (`dotnet test --project <path> --report-trx --results-directory <dir>`), producing the same TRX schema the existing result parser already understands. The `--project` flag is required, not optional: a bare positional path was confirmed working on .NET SDK 10.0.400 but rejected outright on 10.0.204 ("Specifying a project for 'dotnet test' should be via '--project'") — `--project` was verified to work identically on both. On the .NET 10 SDK the legacy VSTest-mode MTP bridge is hard-removed, so this requires the target repo's `global.json` to opt into the native mode (`"test": {"runner": "Microsoft.Testing.Platform"}`) — `test_run` throws an actionable error naming this when it's missing. An omitted `projectName` now routes through this same MTP-aware path when the workspace was loaded directly from one `.csproj` (the normal single-project call shape used by `validate_workspace`/`workspace_fork_apply`, not proof of an ambiguous target); a genuinely multi-project workspace containing an MTP-only project without `projectName` throws an actionable refusal instead of silently running the classic VSTest path and skipping that project's tests. A caller-supplied `--filter` is translated to MTP's `--treenode-filter` syntax; using AND/grouping/negation, or naming a property other than `FullyQualifiedName`, throws an actionable error instead of a silently-wrong translation. Because `FullyQualifiedName~` is a "contains" operator, not "equals", a value can be exactly as consistent with naming a whole class as with naming one complete test, and that ambiguity can't be resolved from the string alone — every parsed filter atom is now checked against the target project's actually-discovered tests, and an atom that doesn't name a real one is declined rather than silently mistranslated (the `test_discover`/`test_related` round trip, which always names a real, complete test, is unaffected). OR-ing alternatives within one path segment is valid MTP grammar (confirmed correct by the MTP maintainer's own reflection probe), but a live production project reproduced it silently matching zero tests — the cause was an open bug in TUnit's own client-side pre-filter (thomhurst/TUnit#6026, not an MTP defect) discarding every test descriptor before MTP's real filter ran, fixed in `TUnit.Engine` 1.46.0. `test_run` now reads the target project's actual restored `TUnit.Engine` version from `project.assets.json` and only emits the OR shape when it's known to be at or above that fix; otherwise it throws, naming the resolved version (or that none could be determined) and the required upgrade. Note: OR-ing full method-qualified paths across different classes remains unsupported regardless of version — that's an unsafe cross-product this translator has no way to represent, though TUnit's grammar does support OR-ing bare class names (no method) within one class segment, which this translator's `FullyQualifiedName`-only input model can't express either way. The `global.json` opt-in check now tolerates the comments and trailing commas the format officially allows (a naive JSON parse would otherwise reject a validly-commented, correctly-opted-in file and silently fall back to assuming VSTest mode) and no longer throws when `test.runner` isn't a JSON string.
