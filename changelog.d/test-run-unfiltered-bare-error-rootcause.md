- **Fixed:** the confirmed root cause of the bare "An error occurred invoking 'test_run'" (no `category`, no `schemaHint`, no `_meta`) reported across multiple retros on large/unfiltered runs: `WorkspaceExecutionGate`'s own per-request timeout (default 2 minutes, `ROSLYNMCP_REQUEST_TIMEOUT_SECONDS`) armed an internal `CancellationTokenSource` distinct from the caller's ambient token. When it fired first — routine for a `dotnet test` run past 2 minutes, well before the 10-minute `TestTimeout` would ever trigger the existing structured Timeout envelope — the resulting `OperationCanceledException` was deliberately rethrown unclassified (so genuine client cancellation reaches the MCP protocol-level cancel path), but the MCP SDK's own top-level `tools/call` catch-all only recognizes cancellation tied to the AMBIENT request token, so it fell through to its own hardcoded fallback string, bypassing every one of this server's structured-envelope layers. `WorkspaceExecutionGate.RunPerWorkspaceAsync` and `RunLoadGateAsync` now reclassify a gate-internal-timeout `OperationCanceledException` into a `TimeoutException` before it escapes — mirroring the pattern `GatedCommandExecutor.ExecuteAsync`/`WorkspaceValidationService` already use for their own internal timeouts — which `ToolErrorHandler.ClassifyAndFormat` already maps to `category="Timeout"`. True caller-initiated cancellation is untouched. This affects every workspace-gated tool, not just `test_run`, but `test_run` is by far the most likely to exceed the 2-minute gate ceiling in practice. (test-run-unfiltered-bare-error-rootcause)
- **Fixed:** `test_run` also no longer risks an opaque failure on a run with a genuinely large number of failing tests, independent of the timeout fix above: `dotnet test` can produce valid TRX output (not crash) while many tests fail, and each `TestFailureDto.Message`/`StackTrace` was unbounded AND the `Failures` list carried every failure with no cap — unlike `StdOut`/`StdErr`, which `DotnetCommandRunner` already bounds to 12000 chars. `DotnetOutputParser` now head-truncates each failure's `Message`/`StackTrace`, and `test_run` now paginates the `failures` array (`failuresOffset`/`failuresLimit`, default limit 25) with `failuresTotal`/`hasMoreFailures` metadata — the same payload-budget pattern already used by `test_discover`'s offset/limit pagination. Aggregate `Total`/`Passed`/`Failed`/`Skipped` counts always reflect the full run, never truncated. This hardening is real and worth keeping, but was never confirmed (via measurement against the actual MCP output cap) as the cause of the recorded bare-error repros — kept as defense in depth. (test-run-unfiltered-bare-error-rootcause)
